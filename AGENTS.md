# Project entry points

- `src/extension.ts` registers the VS Code custom editor; `CsvDocument.ts` owns document lifecycle; `EngineClient.ts` communicates with the worker.
- `src/engine/CsvFile.ts` owns chunked indexing, querying, editing, and saving; `src/engine/worker.ts` is the worker entry point.
- `src/webview/grid.ts` mounts the UI; `CsvGrid.ts` owns table interaction and `style.css` owns styling. Cross-layer messages are defined in `src/protocol.ts`.
- Save preserves document row and column order; row and column dragging are undoable content changes. Pinning and visibility affect only the view. Export current view writes filtered/sorted rows and visible columns to a separate file. Before overwrite apply configured backup policy (enabled, 500 MB total budget, 50 MB prompt threshold by default); backup failure blocks overwrite unless the user explicitly chooses to skip that backup.
- English is the default for the interface, documentation, source comments, and samples. Settings can switch the interface to English or Simplified Chinese and remember the preference. CSV content is never translated. Specialized tests may contain Unicode and non-English fixture data.
- The example directory contains exactly `complex.csv` (small, varied formats) and `large.csv` (large performance sample). Both are generated by `src/SampleCsv.ts`; maintain this generator for project fixtures and tests. Examples are excluded from the VSIX.
- After changes run `npm run typecheck`, `npm test`, and `npm run build`. `npm run package` writes a local VSIX to `release/`.
- UI changes also require `npm run test:ui`, using Chromium Headless Shell for important flows and narrow layouts. Before the first run use `npx playwright install chromium --only-shell`. Configuration is in `playwright.config.ts`; real-engine browser boundary tests are in `tests/browser/grid.spec.ts`. Large-file support requires measurements on real files.
- Debugging and automation must not start, display, focus, or activate desktop VS Code windows, extension hosts, or browsers. Prefer Node checks, builds, and genuinely headless browsers. An isolated profile isolates data; it does not make a desktop app headless.
- `dist/smokeTest.js` requires desktop VS Code and must not run as an automated headless check. Run it only when headless validation is insufficient and the user explicitly authorizes that particular desktop session. If a window cannot be kept hidden, explain the limitation instead of repeatedly trying launch flags. Do not reload, close, or reopen the user's VS Code windows. Install updates through the background CLI; let the user choose when to reload.

- Runtime confirmations, input and backup preferences use the editor-owned HostPrompt/EditorUi boundary. Cancel on editor disposal or failed delivery; only explicit Choose another location opens the system Save dialog. Initial encoding recovery may use native pickers before an editor exists.

- Browser fixtures include VS Code webview default inherited scrollbar styles. Keep that host boundary when changing Table or Text scrolling so custom native scrollbar width and persistent tracks are verified under actual host inheritance.
